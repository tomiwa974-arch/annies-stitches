# Guest shopping and fitting requests

Guests can save products to their cart and wishlist without signing in. Selections persist in local storage in that browser. Cart rows distinguish product, size and colour. Checkout requires an active account and returns the shopper to `/store?checkout=1`, opening their cart for review rather than placing an order automatically.

After login or registration, the shared profile component transfers guest selections to the account through the authenticated `/api/shopping/merge` endpoint. The store also waits for this merge before loading account lists. Existing cart quantities are added, wishlist entries are deduplicated, and a guest-list UUID prevents repeated transfers from duplicating items. Local selections are cleared only after a successful transfer. Product descriptions and prices come from the database; checkout rechecks stock and price. Products deleted or deactivated before transfer are excluded. Guest selections belong to the browser until transferred; account selections belong to the signed-in user.

Guests may complete a fitting form, but sending it saves a draft in IndexedDB and opens login. The draft includes the selected reference image. Login and registration return to the fitting form, restore its contents, and let the user review and send it. The booking endpoint independently requires authentication and records `user_id`. Notifications find owned fitting requests by user ID, with an email fallback for legacy requests lacking an owner. A successful request clears the local draft.

Migrations add `guest_list_merges`, fitting ownership, and a cart unique key that includes colour. Browser storage must be available for guest selections and fitting drafts. Functional tests cover protected checkout, idempotent merging, existing account lists, variants, trusted prices, protected fittings and ownership. Browser checks cover guest persistence, checkout through registration, and a fitting draft with its image through login and submission.
